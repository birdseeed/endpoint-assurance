Guide 03

Configuration assurance

When Patched reports a control result, that is a specific, checkable claim, not a vibe. It means the device passed the controls in the CIS Level 1 benchmark that apply to it. Here's exactly what's measured and what a passing result proves.

The benchmark

We score against the CIS Level 1 (L1) Benchmark: the Center for Internet Security's consensus baseline of essential, low-friction hardening settings, published separately for macOS and Windows. Level 1 is deliberately the "sensible defaults every organisation should meet" tier: it raises the security floor without breaking the way people work. (Level 2, the stricter high-security tier, is out of scope for standard scoring.)

Concretely that's things like: disk encryption on, the firewall enabled, Gatekeeper enforcing signed software, the screen locking on idle, automatic security updates turned on, remote access surfaces switched off, and a sane password policy and admin-account count.

How a control is scored

Each control compares one observed signal from the device against an expected value. Every device control gets one of four results:

ResultMeaning
PassThe observed value satisfies the control.
FailThe observed value does not satisfy the control. This is what shows up as a finding to fix.
Not applicableThe control doesn't apply to this device (e.g. an Apple-silicon-only check on an Intel Mac).
UnknownThe signal couldn't be read. We treat unknowns conservatively per control, rather than silently assuming "pass".

That last point matters: a control we couldn't verify is never quietly counted as compliant. Where the safe assumption is "not secure", we say so.

What's always checked vs. tunable

Not every organisation wants every control scored identically, so the rule set is tiered:

  • Always-on controls: the core CIS L1 essentials. These are evaluated on every device, every time.
  • Per-policy controls: the wider CIS L1 surface, collected on every device but scored according to your organisation's policy, so you can match the benchmark to how you actually operate. Exemptions are explicit and recorded, not buried.

Rules are data, not buried code, so adding a control, adjusting your policy, or recording an exemption is a configuration change with an audit trail, and it can be re-applied to your existing history.

Compliance score, honestly

At the estate level your score is the average compliance across devices, not a single global pass/fail ratio, so one badly-configured laptop in an estate of a hundred reads as roughly one percent of impact, not as estate-wide failure. The point is to show you where to act, in priority order, rather than to produce a scary headline number.

How it maps to the frameworks auditors ask about

CIS L1 isn't an island. Each control we score carries mappings to the control frameworks you're likely to be assessed against, so the same evidence answers several questions at once:

FrameworkWhat the mapping gives you
NIST SP 800-53 r5The corresponding US federal control IDs.
ISO/IEC 27001:2022The relevant Annex A control references.
UK Cyber EssentialsThe Cyber Essentials category each control supports.

So a passing Patched report is evidence you can hand to an auditor, not just an internal dashboard number.

What it does (and doesn't) prove

A compliant device means: at the time of its most recent snapshot, it passed the CIS L1 controls that apply to it, scored against your policy, with unknowns handled conservatively. It is a strong, evidenced baseline of endpoint hygiene.

It is not a claim that the device is un-hackable, nor a substitute for the rest of a security programme (identity, network, backup, training). CIS L1 is the floor done properly and proven continuously. For most SME estates, that's exactly the gap that was open.
