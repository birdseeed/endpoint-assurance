# Patched Updater — endpoint (privileged daemon)

The root-side of the endpoint agent. Collects assurance evidence, maintains the
signed agent-config and posture caches, writes the status file the menu bar app
reads, and reports to the ingestion API.

## What this bundle ships, and what it deliberately does not (PAT-1505)

The bundle `tools/build-bundle.sh` produces is **assurance-only**, and it is the
only bundle that is built or distributed. The deployment engine is not in it.

That is a build-time decision, not a runtime one, and the distinction is the
whole point. The daemon's `AGENT_TIER` gate is real and stays, but it only
decides what runs; it does not decide what is on disk. This bundle installs as
root on prospect machines during a pre-sale assessment, and a reviewer reads
what is installed, not what a flag currently gates off.

The engine sources remain in this repository, untouched. PAT-1481 may bring a
narrow, separately scoped and separately pentested macOS executor back as an
opt-in add-on. Not shipped is not deleted.

Still in the tree, never in the bundle: `engine/Installomator.sh`,
`patched-install.sh`, `patched-uninstall.sh`, `labels-allowlist.txt`,
Installomator's `LICENSE` and `NOTICE` (Apache 2.0 §4 attribution travels with
the covered work, and the covered work is no longer distributed here), and the
actuation LaunchDaemons `com.patched.install-check` and
`com.patched.uninstall-check`.

Retired and deleted (PAT-2245, the signed app catalogue is retired end to end):
the catalogue poller, its verifier and the 4-hourly `com.patched.catalogue-poll`
LaunchDaemon. `install.sh`, the `.pkg` postinstall and `uninstall.sh` still boot
that daemon out and delete its plist, script and cache (`catalogue.json`,
`catalogue.etag`, `catalogue.indeterminate-since`, the fetch lock) on any Mac
an older release left them on.

Upgrading over a pre-PAT-1505 agent purges all of the above from the machine —
see `install.sh`'s `LEGACY_LAUNCHDAEMONS` / `LEGACY_BUNDLE_FILES`. Without that
step an "assurance-only" install would leave the old engine resident and its
daemons still firing every 15 minutes.

## Legacy execution containment (PAT-1481)

The shared signed agent-config contract has a `legacy_app_execution_enabled`
boolean. Every retained macOS executor treats any absent, null, malformed or
false value as deny. Immediately before each retained app-execution seam it
also requires the device not to be suspended, a successful config heartbeat
within 24 hours (`CONFIG_HEARTBEAT_MAX_AGE_SECONDS` in the shared evaluator),
and a digest matching the verified commit. It hashes and parses the same
in-memory config snapshot, capped at 1 MiB with duplicate JSON keys rejected,
so policy parsing cannot race a path swap after the hash or consume unbounded
memory. The evaluator opens root-owned, non-group/other-writable state and
credential directories without following symlinks, then opens each cache file
relative to the trusted directory descriptor and requires root ownership and a
non-writable regular-file mode. Suspension is checked both before and after
that snapshot. Only the exact JSON boolean `true` then allows a
legacy app install, update, uninstall, mandatory-install or rollout path to
reach its existing gates. It is defence in depth, not an entitlement: tier,
ring, queue and operation-specific checks still decide whether anything
executes. With the signed app catalogue retired (PAT-2245) no label has a
verified hash, so the retained install path refuses every install.

The release bundle includes `patched-legacy-app-execution-gate.py` in
`manifest.sha256`. Every caller requires exactly one matching manifest entry
and re-hashes the helper immediately before invoking it. A missing, unlisted,
duplicated, symlinked or replaced helper therefore denies execution. Authority
denials are reported as terminal `authority_refused` outcomes with
`execution_authority_refused` detail; they are never rewritten as successful
scans or retryable app-running deferrals.

On an installed endpoint the config, digest and heartbeat live in the
root-owned `/Library/Application Support/Patched` state directory, created by
the root installer. This protects the evaluator from an unprivileged local
user swapping its cache entries. It is not, and does not need to be, a defence
against root compromise: root can replace the LaunchDaemon or trusted bundle
as well as these files.

This switch is deliberately not consulted by the assurance paths retained in the
bundle: configuration fetch, inventory/assurance collection, OS-update policy,
app-control reporting, browser-extension controls, approved-admin assurance,
decommission, agent self-update, and evidence/status/provenance reporting remain
under their existing gates.

## Retained Application Control authority

`app_control_authority` is a separate signed authority with `report`, `block`,
and `enforce` values. `report` keeps app allowlist reporting only; `block` also
permits browser-extension blocklist reconciliation; `enforce` additionally
permits approved-admin demotion and browser-extension removal. Missing, null,
malformed, noncanonical, duplicate-key ambiguous, or unknown values resolve to
`report`.

It is independent of the projected `tier` and never authorises legacy package
install, update, uninstall, removal, mandatory-install, rollout, or the
ADR-0011 macOS executor. Those are not implemented by this authority and
remain behind `legacy_app_execution_enabled` plus their existing fail-closed
operation-specific gates.

## Trust model (v1 — no MDM required)

Trust is rooted in the **bundle integrity manifest**, not an MDM channel.
MDM/Intune is never required; it is an optional delivery mechanism only.

```
Release tag
  └── tools/build-bundle.sh
        ├── copies the assurance-only script/plist set (no deployment engine)
        ├── generates manifest.sha256   (SHA-256 of every bundle file)
        ├── asserts the manifest and the bundle directory describe each other
        │   exactly — no ghost entries, no shipped-but-unverified files
        └── stamps install.sh with EXPECTED_MANIFEST_HASH = sha256(manifest.sha256)

GitHub Release tarball
  └── install.sh  (EXPECTED_MANIFEST_HASH baked in)
        ├── verifies sha256(manifest.sha256) == EXPECTED_MANIFEST_HASH  ← v1 trust anchor
        ├── copies bundle to /usr/local/patched-updater/
        └── verifies every deployed file against manifest.sha256

Runtime (every daemon run)
  └── patched-update.sh verify_bundle()
        └── verifies every file against manifest.sha256 before executing
```

The chain of trust: `install.sh` carries the expected hash of `manifest.sha256`.
`manifest.sha256` lists the hash of every file in the bundle. The daemon
re-verifies the bundle on every run. A tampered release is caught at install
time; a tampered deployment is caught before the daemon executes anything.

The similarly named JSON label manifest is not executed on endpoints, and as of
PAT-1505 neither the engine nor the derived authorization allowlist is shipped
at all, so no shell engine receives labels on a current endpoint. The label
manifest, its integrity gate (`ci/validate-labels.py`) and the `pkgindmg`
selection rules PAT-1385 tightened all remain in the repository and in CI,
covering the quarantined sources rather than anything on a customer machine.
PAT-1403 tracks the broader single-source migration.

**v2 (PAT-50):** the bundle will be shipped as a signed, notarised `.pkg`,
replacing this hash-pinned trust root with an Apple-signed chain.

## Install (v1 — no MDM, runs as root)

Download the release tarball from the GitHub Releases page, then:

```sh
tar -xzf patched-updater-endpoint-vX.Y.Z.tar.gz
cd patched-updater-endpoint-vX.Y.Z
sudo bash install.sh
```

`install.sh` will:
1. Verify `manifest.sha256` matches the hash baked into this release (v1 trust anchor).
2. Copy the bundle to `/usr/local/patched-updater/` (root:wheel; scripts 755, data 644).
3. Verify every deployed file against `manifest.sha256`.
4. Purge any quarantined or retired component left by an older install: boot
   out and remove the `install-check`, `uninstall-check` and retired
   `catalogue-poll` daemons, delete the engine scripts and allowlist from the
   bundle directory, and delete the retired catalogue cache (PAT-2245). Runs
   only after the new bundle is verified in place; idempotent and non-fatal.
5. Create `/Library/Application Support/Patched/triggers/` mode `1733`, root-owned.
6. Install three LaunchDaemon plists to `/Library/LaunchDaemons/` and load each
   (`launchctl bootout` + `bootstrap system`, idempotent on upgrade):
   `com.patched.update`, `com.patched.config-poll` and `com.patched.posture-poll`.
   The posture poller is the sole writer of `posture.json`; it verifies the
   signed response before committing its decoded body.
7. Warn clearly if `/etc/patched/{tenant-id,bearer-token,hmac-secret}` are missing.

Credentials at `/etc/patched/` must be provisioned separately (shared with the
inventory agent). The daemon will refuse to run until all three are present.

**Intune:** the tarball can be delivered via Intune Platform Script as an optional
convenience. Run `sudo bash install.sh` from the extracted directory. The trust
model does not depend on the MDM channel.

## Uninstall

```sh
sudo bash uninstall.sh
```

Boots out and removes every LaunchDaemon `install.sh` installs, plus the three
quarantined deployment daemons a pre-PAT-1505 install may still have loaded.
Its list is a deliberate superset of the installer's: uninstall has to clean up
the machine it finds, not the machine the current bundle would have produced.
Removes the bundle and clears the triggers directory and `update-status.json`.
Does **not** remove `/etc/patched` credentials.

## Build a bundle locally

```sh
bash tools/build-bundle.sh
# → dist/patched-updater/   (bundle)
# → dist/install.sh         (manifest hash stamped)
# → dist/uninstall.sh
```

The build is deterministic: given identical source files it always produces the
same `manifest.sha256`. It no longer needs `jsonschema` or any Python, because
it no longer emits the derived label allowlist. The build fails if the manifest
and the bundle directory disagree in either direction, so a file cannot ship
without a hash and a hash cannot name a file that is not there.

## Local testing

```sh
# Override paths for a test run (test-only; never set in the production plist)
sudo PATCHED_BUNDLE_DIR=/path/to/dist/patched-updater \
     PATCHED_API_URL=http://127.0.0.1:8080 \
     /path/to/dist/patched-updater/patched-update.sh

cat "/Library/Application Support/Patched/update-status.json" | python3 -m json.tool
```

The `PATCHED_*` env vars are test-only overrides. The production LaunchDaemon
plist (`com.patched.update.plist`) sets none of them, so the daemon always runs
against the secure hardcoded defaults.
