# Agent-script and collector footguns (macOS and Windows)

Moved from this repo's `AGENTS.md` on 2026-09-28, text unchanged, so that sessions not touching collector code stop loading about 30KB of it on every start. `AGENTS.md` keeps a pointer. Despite the historical heading below, the entries cover both the macOS and Windows collectors.

## macOS agent-script footguns (collector + endpoint)

These bit us on the shell side of the macOS agent; they moved here with the collector under PAT-384 (also recorded in the workspace anchor `~/CLAUDE.md`). `shellcheck` and `zsh -n` (the `macos-collector-lint` / `verify-engine` checks) catch syntax, not these:

- **zsh `path` array trap.** Never use `path`, `cdpath`, `fpath`, `manpath`, `infopath` as loop or local variable names in zsh — they're bound to their uppercase scalar via `typeset -T`, so assigning to them silently corrupts `$PATH`. Neither `shellcheck` nor `zsh -n` catches it. See `macos/patched-collect.sh` for the warning comment.
- **zsh read-only special scalars.** A distinct failure mode from the `path` family above: `status` (tied to `$?`), `pipestatus`, and `history` are *read-only* specials, so `local status=...` inside a function throws `read-only variable: status` and aborts the function on that very line — an entire code path then silently never runs. Both traps bit the decommission work (PAT-1109): a `local status="$1"` in the status-report helper meant the terminal report never executed, and a `local path="$1"` in test helpers corrupted `$PATH`. Neither `shellcheck` nor `zsh -n` catches either. Rule of thumb: never reuse a zsh special-parameter name as a local or loop variable — prefix it instead (`report_status`, `dest_path`).
- **Privileged command resolution (PAT-2394).** Retained endpoint update, config, posture, enrolment, log-upload and decommission scripts reset PATH to `/usr/bin:/bin:/usr/sbin:/sbin` before any external command. User-owned `/usr/local` directories, inherited PATH and test overrides are not trusted. `/usr/bin/python3` must be executable and pass an isolated startup probe before side effects; unavailable or unusable runtimes exit with an explicit error, without downloading a replacement. Tests inject stubs only into owned scratch source copies through `ci/privileged_script_fixture.py`, which rejects zero/multiple PATH matches before invocation. Keep a loopback API fallback even when curl is stubbed. The portable check does not replace authorised disposable-Mac installed rejection proof.
- **Privileged entrypoint ancestry (PAT-2395).** A root-owned script is only as safe as every directory above it: whoever owns the directory can replace the name. The collector and uploader LaunchDaemons therefore execute from `/Library/Patched`, not `/usr/local/bin` (Homebrew-owned on many Macs). `macos/install.sh` calls `patched_verify_ancestry "$AGENT_DIR" "$ANCESTRY_ANCHOR"` before its first write and again after creating the tree: every existing component from `/` down must be a real directory, uid 0, not group- or other-writable; a symlink, a user-owned component or an existing untrusted tree is refused, never repaired, and nothing is written. Legacy `/usr/local/bin` entrypoints are deleted only after the new tree is installed and the jobs reloaded; `/usr/local` and `/usr/local/bin` are never chowned or chmodded. The helper block between the `PATCHED_ANCESTRY_HELPERS` markers must stay self-contained, because `ci/test_privileged_entrypoint_ancestry.py` sources it alone and replaces `patched_ancestry_probe` (tests cannot chown to root). The three scratch-copy tests under `macos/` rebase `AGENT_DIR`, `LEGACY_BIN_DIR` and `ANCESTRY_ANCHOR` with anchored `sed`; if one of those lines is reworded the `sed` stops matching and the test would run against real paths, so change both together. Not covered: `/usr/local/patched-updater` (endpoint bundle) and `/var/lib/patched/collector` (bootstrap loader). Passing this test is source evidence; replacement-denial by a standard user still has to be shown on an installed Mac.
- **Installer ACLs, command paths and stat kinds (PAT-2398).** Three things the PAT-2395 ancestry check did not cover in `macos/install.sh` and `macos/uninstall.sh`. *ACLs:* owner and mode bits say nothing about ACLs, so `patched_verify_ancestry` now also runs `patched_ancestry_acl_check` on every component. It reads `/bin/ls -lden` (numeric, so a principal is the UUID stored in the entry, never a name from the directory service) and refuses any allow entry that gives a principal other than the uid 0 UUID (`FFFFEEEE-DDDD-CCCC-BBBB-AAAA00000000`) a permission outside a fixed read-only list. Groups are never trusted, `wheel` and `admin` included. Deny entries are ignored, entry order is not evaluated (a write grant masked by a deny is still refused), and a listing that cannot be read or parsed is a refusal. Stock macOS has no allow entry on `/` or `/Library`; a Mac where management tooling added one will now be refused with the component and principal named, which is intended. *Command paths:* both scripts reset PATH to `/usr/bin:/bin:/usr/sbin:/sbin` (the PAT-2394 convention, which also covers `endpoint-install.sh` and `endpoint-uninstall.sh` as children) and call every external tool by absolute path. `ci/test_privileged_installer_trust.py` scans every command word, including those in functions, pipelines and command substitutions, against an allowlist of builtins, functions defined in the file and named absolute tools; adding a tool means adding it to `ALLOWED_TOOLS` there on purpose. The scanner (`ci/privileged_command_words.py`) raises on shell it cannot read, so backticks, process substitution and `eval`/`exec`/`source` fail the guard instead of slipping past it. Because the scripts no longer look at PATH, a stub on the caller's PATH does nothing: the scratch-copy tests rebase `/usr/bin/id`, `/bin/launchctl` and the PATH line inside the copy and refuse to run a copy where that `sed` did not match. *stat:* the probe reads the numeric file type (`stat -f %Hp`: 4 directory, 12 symlink) instead of matching the English words `%HT` prints. Not covered: exported shell functions and `BASH_ENV` in the caller's environment (sudo strips both by default), the endpoint installer's own bare command words, and a change to the tree between the check and the write. Passing is source evidence; the ACL refusal and a poisoned-PATH install still have to be shown on an installed Mac.
- **Endpoint installer pair and trigger command paths (PAT-2420).** `endpoint/install.sh`, `endpoint/uninstall.sh`, `macos/patched-collect-trigger.sh` and `macos/patched-uninstall-trigger.sh` now follow the same convention as the macOS installer: one literal `export PATH="/usr/bin:/bin:/usr/sbin:/sbin"` before the first command and every external tool by absolute path, enforced by the allowlist and poisoned-PATH runs in `ci/test_privileged_installer_trust.py` (`GUARDED` lists the scripts). The endpoint pair inherited a reset PATH from `macos/install.sh` but had none when run directly, and stock macOS `sudo` keeps the caller's PATH. The `PATCHED_LEGACY_PURGE` block is byte-identical in `tools/pkg-scripts/postinstall`, so the block must be changed in both files together; the whole of `postinstall` (the only script in `tools/pkg-scripts/`) follows the convention and is in `GUARDED`. The triggers are not installed, scheduled or shipped by anything in this repository: a person runs them, as an ordinary user who reaches root through the `sudo` calls inside, or under `sudo`. `sudo` is allowed only in those two files and only for the fixed entrypoints the test names; `awk` only with the literal `'{print $1}'`. *Stubbing in tests:* a shell function or a stub on PATH can no longer stand in for `id` or `launchctl` in these scripts. Rebase the absolute path onto a stub in the scratch copy and refuse a copy that still names the real tool, as the `endpoint/test-*cleanup*.sh` and `macos/test-install-endpoint-bundling.zsh` tests do. *Exported functions and `BASH_ENV` are deliberately not defended against in the scripts.* Measured on `/bin/bash` 3.2.57: an exported function does shadow a builtin (`echo`, `exit`, `[`) in a child `bash script`, and `BASH_ENV` is sourced before the script's first line, so nothing inside the script can undo it. An absolute-path command word is not affected: bash refuses to import a function whose name contains a slash. Nobody who is not already root can put either into these scripts' environment by a documented route: `sudo` removes every variable whose value begins with `()` and `BASH_ENV`/`ENV` unless sudoers was edited to keep them (sudoers(5), Command environment), MDM and launchd start them with a clean environment, and `patched-decommission.sh` runs from a LaunchDaemon. `bash -p` would ignore both, but only where the invoker passes it; the documented `sudo bash install.sh` form bypasses a shebang, and a re-exec written inside the script would itself be built from shadowable builtins. If a new invocation route keeps the caller's environment (a setuid wrapper, a sudoers `env_keep` or `SETENV` rule), close it at that route.
- **Uninstall verifies ancestry before deleting (PAT-2420).** `macos/uninstall.sh` ran `rm -rf /Library/Patched` as root with no check, so whoever controlled a component of that path chose what root deleted. It now calls `patched_verify_ancestry "$AGENT_DIR" "$ANCESTRY_ANCHOR"` before its first delete and again on the line guarding the recursive delete. When the check fails the tree is left untouched and named on stderr, everything not under that path is still done (daemons booted out, plists removed, legacy entrypoints and shared state cleaned, `--purge` honoured, `endpoint-uninstall.sh` run) and the exit status is 2. A tree that does not exist is not checked, so a legacy-only machine under an untrusted `/Library` still uninstalls with status 0. The window between the check and the delete is real and does not matter: a passing check means only root can rename or replace any component, and `rm -rf` never follows a symlink inside the tree. *The helper block is duplicated on purpose.* The script also ships alone as `macos-uninstall.sh` in the endpoint bundle and the decommissioner runs that copy standalone, and neither bundler inlines into it, so it cannot source the block from `install.sh`. The copy between the `PATCHED_ANCESTRY_HELPERS` markers must stay byte-identical to `macos/install.sh`; `ci/test_privileged_installer_trust.py` fails on drift. *Decommission:* `patched-decommission.sh` ignores the uninstaller's exit status and checks the filesystem, so a refused tree fails `verify_core_removed`, the platform is sent `failed` ("will retry on next boot"), and the job retries once per boot, not in a loop. The agent is stopped and unloaded on the first pass. With `purge: true` the purge step is never reached while the tree remains, so credentials and queue stay until someone repairs the path.
- **Windows equivalent of the entrypoint boundary.** The Windows agent's only installed executable is `%ProgramFiles%\Patched\Patched.Service.exe`, installed per-machine by the MSI and run as `LocalSystem` (`windows/installer/Product.wxs`). The MSI sets no ACL of its own on that directory and does not verify one at install time: the directory inherits the `%ProgramFiles%` default DACL, which the source records as TrustedInstaller FullControl plus inherit-only full control for TrustedInstaller, SYSTEM, Administrators and CREATOR OWNER (`WindowsInstallationEvidence.cs`, PAT-2116). That standard users cannot write there is the Windows default this relies on; no code in this repository asserts it at install time. So the boundary that `/Library/Patched` plus the ancestry check provides on macOS is, on Windows, the operating system's Program Files ACL, not an installer check. What the agent does verify is narrower and happens at run time: before the service starts a copy of itself as a helper, `InstallationEvidenceProbe.PrepareTrustedHelper` requires the running process to be exactly that Program Files path, opens the path with a walk that refuses a reparse point at any component, and checks the directory (`VerifyInstallDirectoryAcl`: owner and writers limited to SYSTEM, Administrators and TrustedInstaller) and the executable (`VerifyExecutableAcl`: SYSTEM and Administrators) before launching; a refusal is reported in agent health as `helper_preflight_refused`. Nothing checks the install directory before the Service Control Manager starts the service itself. The state directories under `%ProgramData%\Patched` are a separate matter: the MSI grants them to SYSTEM and Administrators and `TriggerAcl.cs` re-applies the DACL on each service start.
- **Windows equivalent of the entrypoint boundary.** The Windows agent's only installed executable is `%ProgramFiles%\Patched\Patched.Service.exe`, installed per-machine by the MSI and run as `LocalSystem` (`windows/installer/Product.wxs`). Since PAT-2399 the MSI sets an explicit, protected ACL on that directory and on the executable (SYSTEM and Administrators full control, Users read and execute; `MsiLockPermissionsEx`, guarded by `windows/installer/test_install_directory_acl.py`). A device installed by an older MSI still has the inherited `%ProgramFiles%` default DACL until its next upgrade: TrustedInstaller, SYSTEM and Administrators full control, Users and the application-package principals read and execute, and an inherit-only CREATOR OWNER entry. Both shapes must keep passing the checks below; rejecting the inherited one would stop every agent already installed. What the agent does verify is narrower and happens at run time: before the service starts a copy of itself as a helper, `InstallationEvidenceProbe.PrepareTrustedHelper` requires the running process to be exactly that Program Files path, opens the path with a walk that refuses a reparse point at any component, and checks the directory (`VerifyInstallDirectoryAcl`: owner and writers limited to SYSTEM, Administrators and TrustedInstaller) and the executable (`VerifyExecutableAcl`: SYSTEM and Administrators) before launching; a refusal is reported in agent health as `helper_preflight_refused`. The rule is `InstallDirectoryAclPolicy` (Shared), and it treats a write-capable inherit-only entry for an untrusted principal as a refusal, because it reaches every file later created there; only CREATOR OWNER's is accepted. The same rule runs at service start and before each self-update check (`InstallIntegrityGate`): a failure is reported in agent health as `install_integrity`, self-update apply and staging are refused, and the service keeps collecting so the fault is visible. Read a .NET ACL with raw masks in mind: an inherit-only entry carries unmapped `GENERIC_ALL` / `GENERIC_WRITE` bits that no `FileSystemRights` name matches. This is detection for an unmodified binary, not a control; a replaced executable does not run it. The state directories under `%ProgramData%\Patched` are a separate matter: the MSI grants them to SYSTEM and Administrators and `TriggerAcl.cs` re-applies the DACL on each service start.
- **`set -euo pipefail` is too brittle** for the macOS app-inventory loop — `lipo`/`codesign` return non-zero on launcher stubs. Collector scripts use `set -u` only, with per-section `|| true` defaults.
- **macOS 26 parser changes:** `systemextensionsctl list` uses `*`/`-` markers (not "enabled"/"active"); `bputil --display-all-policies` → parse "Pairing Integrity" (not "Secure Boot"); the screen lock password setting is system-managed from macOS 13 and no longer written to `com.apple.screensaver`, so on 13 and later `collect_screensaver` reads `sysadminctl -screenLock status` as the subject user (`launchctl asuser <uid> /usr/bin/sudo -u <user>`, output captured with `2>&1` because it arrives via NSLog on stderr) and never the plists: `screenLock delay is N seconds` is `"Yes"` with delay N, `delay is immediate` is `"Yes"` with 0, `screenLock is off` is `"No"` with a null delay, and anything else (a non-zero exit, a missing binary, `Unknown state for screenLock`, more than one screenLock line, or an unparseable `OS_VERSION`) is `"Unknown"` with a null delay, never `"DefaultAssumed"` (PAT-1743). On macOS 12 and earlier, a `com.apple.screensaver` plist missing `askForPassword` = default-secure (emit as `"DefaultAssumed"`), but only after every candidate plist was actually read; no user, an unresolvable home, an unreadable or corrupt plist or a wrong-type value emits `"Unknown"` (PAT-1710). The current-host `ByHost/com.apple.screensaver.<IOPlatformUUID>.plist` outranks the main plist (CFPreferences resolves current-host first, confirmed on macOS 26), ByHost plists named for another hardware UUID are ignored, and an unreadable ByHost plist makes the result `"Unknown"` even when the main plist sets the key (PAT-1722).
- **Per-user CIS signals need a deliberate subject user.** `collect_screensaver` reads the console user (`console_user` in `macos/lib/common.sh`, `stat -f %Su /dev/console`), the same subject `collect_user_prefs` uses, with `root`, `loginwindow` and empty meaning nobody is logged in. With nobody logged in, `user_prefs.sh` reports null, while screensaver (a non-nullable field) falls back to `FIRST_USER`, the lowest local account with UID 500 or above, and logs `no console user logged in, reading the lowest-UID local account (<user>) instead` to stderr so that evidence is not mistaken for a logged-in user's. A console user whose home cannot be read is `"Unknown"`; `FIRST_USER` never stands in for a logged-in user. The payload carries one screensaver value, not one per user (PAT-1723).
- **The screen saver inactivity interval is not the lock delay, and 0 is "never".** CIS 2.10.1 reads `com.apple.screensaver` `idleTime`; `screensaver_delay_seconds` is the separate password grace period (PAT-1746). `collect_screensaver` reads idleTime on every macOS version with one JXA `NSUserDefaults` call run as the subject user (`launchctl asuser <uid> /usr/bin/sudo -u <user> /usr/bin/osascript`), so CFPreferences resolves a profile-forced value over the user's ByHost and any-host values; read as root it would see neither per-user managed nor ByHost values. `screensaver_idle_seconds` is a positive integer, `"NotConfigured"` when the key is not set and every plist in the user's search list (per-user and computer Managed Preferences, the user's any-host and every ByHost plist, `/Library/Preferences`, for the screensaver and global domains) is absent or a readable dictionary (PAT-1775), or null for a failed read, a wrong type or an unset key that cannot be confirmed. tenant-zero on macOS 26.6.2 has no idleTime anywhere and the macOS default is not verified, so `"NotConfigured"` never implies an interval. idleTime 0 means "never start" and is sent as `99999`, the sentinel the Windows agent already uses for `machine_inactivity_limit_seconds` = no limit, because a literal 0 would pass the server's `lte 1200`. `screensaver_idle_seconds_enforced_by_profile` follows the PAT-1720 convention above (PAT-1753).
- **`HW_UUID` is `"Unknown"`, never empty, when ioreg fails or yields no `IOPlatformUUID`.** `collect_hardware` captures ioreg's output and checks its exit status before parsing; a `cmd | awk ... || echo Unknown` pipeline tests awk's status, not the command's (PAT-1723).
- **Managed prefs report the effective value, plus whether a profile enforces it.** `managed_pref_read` (`macos/lib/common.sh`) makes one osascript JXA call per key that returns both the effective value (the whole NSUserDefaults search list, so a local `defaults write /Library/Preferences/...` reads the same as a profile-forced value) and `objectIsForcedForKey`. `collect_managed_prefs` emits each signal unchanged plus a `<key>_enforced_by_profile` companion: JSON `true`/`false`, or `null` when osascript failed. Forced-only reads were rejected because they would fail CIS rules on genuinely configured Macs with no MDM (PAT-1720). The helper returns non-zero when osascript fails: check that status before turning an empty read into a confident "No", and never default the flag to `false`.
- **An unset preference is `"NotConfigured"` only with proof the read could see it.** Compliance signals are a real value, `"NotConfigured"` (read succeeded, setting absent) or null / `"Unknown"` (read failed) (PAT-1767). On macOS 26.6.2 `defaults read` exits 1 with the identical `The domain/default pair of (...) does not exist` line for a missing key, a corrupt plist, a non-dictionary plist and a plist it may not read, and NSUserDefaults returns nil for all of them, so neither the exit status nor the error text alone proves absence. `prefs_defaults_read` (`macos/lib/common.sh`) classifies a `defaults` read as value / absent / failed, `managed_pref_read` reports `MANAGED_PREF_SET`, and a caller only sends `"NotConfigured"` after `prefs_plists_readable` confirms every plist the read could have used is absent or a readable dictionary. The plist check runs only after a read reports absence, so a value that was read is never changed. Numeric signals go into the payload through `json_int_or_notconfigured` (a read number stays a bare JSON integer, `"NotConfigured"` is quoted, anything else is null); once a numeric signal can hold the string, never emit it as `${VAR:-null}`, which writes `NotConfigured` unquoted and breaks the JSON (PAT-1775). `update_deferral_days`, `screensaver_idle_seconds` and `install_log_retention_days` send `"NotConfigured"` for an unset value; `pwpolicy_*` stay null, because a parameter key missing from the global `pwpolicy -getaccountpolicies` output does not prove the control is absent (per-user policies are not read, and a `policyContent` rule can set the same limit).
- **Hardware health reports what it could read.** `hardware_health.collection_status.{battery,storage,disks}` is `complete`, `partial` or `unavailable` (PAT-1720). A failed `system_profiler`, `df` or `diskutil list` is `unavailable`, never "no battery / no volumes / no disks"; a physical disk whose `diskutil info` fails, or lacks a field its row needs, is left out and the section marked `partial` so the server keeps its stored row. The `patched-collect.sh` stub marks all three `unavailable`. Windows (`HardwareHealthCollector` + `HardwareHealthLogic`) emits the same object.
- **Firmware reports what it could read, and nothing read is unavailable.** The Windows `firmware` block (PAT-2262, `DeviceCollector.CollectFirmware` + `FirmwareInventoryLogic`) reads one instance each of `Win32_BIOS`, `Win32_ComputerSystem` and `Win32_BaseBoard` through `WmiInstanceReader`: a query that throws marks every property of that class failed, no instance marks them absent. Each section is `unavailable` when every read failed, `partial` when one failed or a value was unusable, else `complete`; absent values are null in a complete section. The block is `unavailable`, with no sections, whenever no usable value was read at all, including every query succeeding empty (`no_firmware_values`), so an empty or failed collection is never sent as complete. `bios.version` is `SMBIOSBIOSVersion`, not `Version` (the ACPI OEM id). `ReleaseDate` is a CIM datetime: only the date part is used, with no time-zone shift, and anything that is not a real calendar date between 1970 and 2099 is sent as `release_date_raw` (bounded to 64) with the section `partial`. Values over 128 characters or with control characters are dropped, never truncated. `errors` holds fixed codes only. Observation only: nothing says whether firmware is current or vulnerable. The block's exact bytes are pinned in `DeviceCollectorFirmwareTests` and copied into the platform's payload fixtures; change both together.
- **Kernel drivers are identified by hash, a file that cannot be read is a row, and nothing about the blocklist is inferred.** The Windows `kernel_drivers` block (PAT-2263, `KernelDriverCollector` + `KernelDriverInventoryLogic`) merges three sources, deduplicated by resolved path ignoring case: every `*.sys` directly in `%SystemRoot%\System32\drivers` (reparse points are listed, not skipped, so the opener can refuse them as a row), every `HKLM\SYSTEM\CurrentControlSet\Services` subkey with Type 1 or 2 at its unexpanded ImagePath (`\SystemRoot\`, relative-to-SystemRoot, `%SystemRoot%`/`%windir%`, `\??\`, rooted-without-drive and drive paths only; UNC, other variables, `..` and streams are `path_unsupported`; no ImagePath is the I/O manager default `System32\drivers\<name>.sys`), and the kernel loaded-module names from `NtQuerySystemInformation(SystemModuleInformation)` (names only, never the image bases Windows 11 24H2 zeroes; a name with no root or a non-ASCII byte is `loaded_path_unresolved`, never resolved through a code page). Files are opened only through `WindowsInstallationEvidence.OpenLocalFile` (local fixed drive, every component opened with `FILE_FLAG_OPEN_REPARSE_POINT` and refused if a reparse point, held without write sharing), read as bytes and never loaded or passed to WinVerifyTrust. One pass gives flat SHA-256 and SHA-1 plus the Authenticode SHA-256 and SHA-1 (checksum, security directory entry and certificate table left out), which is what both Microsoft's SiPolicy `Hash` rules and loldrivers.io `Authentihash` list; WDAC page hashes and the signer are not collected. Bounds: 1,500 rows (loaded and service rows first), 160 MB per file, 3 GB and 90 s per cycle, 1 MiB on the wire; hashing runs on its own thread and the budget is enforced from outside it, so a read blocked on an oplock costs the budget and no more, and while that worker is still blocked no later cycle starts another (its rows are `time_budget` at once), so a read that never returns costs one thread, not one per cycle. An unreadable, refused, oversized or out-of-budget file stays in the list unhashed with its reason and makes the list `partial`; `file_missing` (a stale service entry) does not. All three sources failing is `unavailable` with no `drivers` key. `enforcement` is always sent: `VulnerableDriverBlocklistEnable` 1/0/absent/other is `enabled`/`disabled`/`not_set`/`unknown`, HVCI is the compliance collector's own `Win32_DeviceGuard` read this cycle kept raw (`ComplianceCollector.LastHvciStatus`, because `hvci_enabled` folds configured and running together and only running forces the blocklist), and `blocklist_enforced` is `yes` only on evidence (blocklist enabled, HVCI running or Smart App Control on), `no` only when all three were read and none forces it, else `unknown`: `not_set` is never read as the Windows 11 22H2 default. The exact bytes are pinned in `KernelDriverCollectorTests` and copied into the platform's payload fixtures; change both together.
- **Windows `mdm_enrolled` is not "Enrollments has subkeys".** Windows creates `HKLM\SOFTWARE\Microsoft\Enrollments` subkeys on devices that were never enrolled (an unenrolled Windows 11 VM had 34: GUID keys with no values, `Context`, and the built-in `Local Authority`, `Deploy Authority` and `Cloud Authority` entries with EnrollmentState 1), so the old presence check reported every device enrolled (PAT-1751). `ComplianceCollector` snapshots each subkey's ProviderID, EnrollmentState and DiscoveryServiceFullURL and `MdmEnrollmentParser` decides: `"Yes"` only when one subkey has EnrollmentState 1, a non-empty ProviderID that is not a built-in authority (case-insensitive), and a non-empty DiscoveryServiceFullURL. EnrollmentType is not used because Microsoft does not document its numeric values. A missing Enrollments key is `"No"`, any registry read exception is `"Unknown"`.
- **Windows screen saver signals come from the console user's hive, and HKLM is deliberately not read.** Group Policy and Intune deliver the CIS 19.1.3.x screen saver settings as User Configuration, so they land in `HKCU\Software\Policies\Microsoft\Windows\Control Panel\Desktop`; the old HKLM-only read reported a policy-configured device as `"Unknown"` (PAT-1747). `ConsoleSessionUser` resolves the SID of the user at the physical console (`WTSGetActiveConsoleSessionId` + `WTSQueryUserToken` + `GetTokenInformation(TokenUser)`, read-only, token closed immediately) and `ComplianceCollector` reads `HKU\<SID>` without ever loading a hive. `ScreensaverPolicyResolver` resolves each value from the user policy, then the user preference (`HKU\<SID>\Control Panel\Desktop`), and nothing else, and emits `screensaver_enabled`, `screensaver_password_required` and `screensaver_timeout_seconds` unchanged, each with a `<signal>_source` companion: `user_policy`, `user_preference`, `not_set`, `no_console_user`, `user_hive_not_loaded` or `read_failed`. `HKLM\SOFTWARE\Policies\Microsoft\Windows\Control Panel\Desktop` is not read: the ADMX defines these settings only under User Configuration, Windows reads them from the user's Policies hive, and nothing is known to apply an HKLM value to a user session, so a stray HKLM `1` ranked above a user's `0` would be a false pass. Re-adding it needs device evidence that Windows honours it; the Service's key reader refuses any path outside `HKEY_USERS\<SID>\`. No console user, an unloaded hive or a failed read is `"Unknown"` with no timeout, and a failed or unusable value never falls through to a lower tier. When both keys were read and neither sets a value (`not_set`), the value is `"NotConfigured"`, timeout included (PAT-1767). Windows keeps `ScreenSaveActive=1` in the preference key when the screen saver is "(None)", so a preference `ScreenSaveActive=1` is `"Yes"` only with a non-empty `SCRNSAVE.EXE`. A resolved `ScreenSaveTimeOut` of `0` means the screen saver never starts, so it and any negative value are sent as `99999` (the estate's "never" value, as for `machine_inactivity_limit_seconds`) with their `_source` unchanged, because they would pass `lte 900` (PAT-1761). Enumerating `HKEY_USERS` is not a substitute: SSH, RDP and service logons load hives too.
- **Windows compliance signals keep absent and failed apart.** Every compliance signal value is a real value, `"NotConfigured"` (the read succeeded and the setting is absent) or `"Unknown"` (the read failed); the macOS agent spells the last one JSON null, and the server's `treat_not_configured_as` defaults to the rule's `treat_unknown_as` (PAT-1767). `ComplianceCollector` reads HKLM through a `RegistryValueReader` that returns a `RegistryRead` (`Present`, `Absent` for a missing key or value, `Failed` for any exception), never a nullable DWORD, and `RegistrySignalMapper` maps it: absent is `"NotConfigured"`, failed or a wrong-type value is `"Unknown"`, and a failed read met before a usable value never falls through to the next key (ASR, auto updates, event log size). `SecurityOptionsParser` sends absent as `"NotConfigured"`; `ServicesFeaturesParser` and `DefenderPolicyParser` keep their per-control absent defaults, but only for a read that succeeded, and omit the signal on a failed read. `auto_updates_enabled` maps `AUOptions` (the Windows Update Agent notification level) 1 and 2 to `"No"` because neither downloads updates on its own, 0 to `"NotConfigured"`, and 3 or above to `"Yes"`.
- **Windows `disks[].device` is the disk's serial, not its model name.** The server matches disk rows on `(device_hardware_id, device_node)`, so the key must be unique per disk and stable across reboots. `HardwareHealthLogic.DiskDeviceKey` sends the trimmed `MSFT_PhysicalDisk.SerialNumber`, falling back to the trimmed `UniqueId` only when the serial was read and is empty, never when the read failed. `FriendlyName` (shared by two disks of one model) is never the key and is logged only; `DeviceId` renumbers and `ObjectId` embeds the computer name. A value with control characters or over 128 characters is not used (no truncation), a disk with no usable key is left out, and disks that resolve to the same key are all left out, each marking `disks` `partial`. MediaType 3 is `solid_state=false`, 4 (SSD) and 5 (SCM) are `true`, and 0 (Unspecified) or any other value is undetermined, so the disk is left out rather than claimed as spinning (PAT-1733). macOS sends `disk0`/`disk1`; the field is an opaque per-device key on both platforms.
- **The local administrator roster reports who it could see, and the count says when it could not see.** `local_admin_count` used to be computed from `dscl . read /Groups/admin GroupMembership 2>/dev/null | awk ... | wc -l`, which swallowed a failed read and counted `0` from the empty output: a Mac whose directory service could not be read looked identical to one with no standing admins, and `0` passes CIS 5.8 outright (PAT-1974). Both agents now check the read and send a failed one as macOS JSON null / Windows `"Unknown"`, never `0`. The account names are structured data and never go into the flat `compliance` bag, whose values are scalars only: they go in the top-level `local_admins` object, `{collection_status, accounts}`, with `accounts` omitted rather than sent as `[]` unless the status is `complete`, the same rule `certificates` follows. macOS reads `dscl -plist` (plain-text `dscl` prints `No such key: GroupMembership` to **stdout** and still exits 0, so only the plist tells an absent attribute apart from a present one) and treats a missing `GroupMembership` as unavailable, because membership can be recorded as `GroupMembers` GeneratedUIDs alone. Windows reads `NetLocalGroupGetMembers` at level 2, not `Win32_GroupUser` (which silently omits members whose SID it could not resolve, undercounting while reporting `complete`) and not `GroupPrincipal.GetMembers` (which throws part way through enumeration on one unresolvable SID, and whose `FindByIdentity(ctx, "Administrators")` is a literal English name that returns null on a localised Windows); the group is located by its well-known SID S-1-5-32-544. Three Windows decisions are settled in `LocalAdminLogic` with a test each: a directory group such as `CONTOSO\Domain Admins` is reported with `principal_type: "group"` but **not counted**, because its membership is opaque from the device and counting it as one would be a number the agent cannot evidence; an unresolvable SID is reported as `principal_type: "unresolved"` under the raw SID as its name and **is** counted, because dropping it would undercount a real admin path; and no built-in is excluded the way macOS excludes `root` — the RID-500 account is sent with `builtin: true` and counted, because whether it is enabled is exactly the risk and cannot be read from group membership. Test the RID with the whole last component rather than `EndsWith("-500")`. The two agree on every well-formed SID (a string ending `-500` can only have `500` as its last component), so this is a clarity and single-implementation rule, not a defect fix; `LocalAdminLogic.IsBuiltinAdministrator` is the one implementation and `AdminEnforcer` calls it (PAT-1989).
- **A `python3 - <<'PYEOF'` heredoc and a pipe cannot both feed stdin.** `printf '%s' "$data" | "$PYTHON3" - <<'PYEOF'` hands python the *data* as its program and the parse fails on every run, so the collector reports the section unavailable forever and looks merely degraded. Neither `zsh -n` nor `shellcheck` catches it. The established house form passes the data through a file in `$PATCHED_TMPDIR` as `argv[1]` (`"$PYTHON3" - "$_TMP" <<'PYEOF'`), as the pwpolicy and authorizationdb parses in `macos/lib/auth.sh` do. Caught in PAT-1974 only because the new code was exercised against a real read before it was called done.
- **Certificates report what they could read.** Top-level `collection_status.certificates` is `complete`, `partial` or `unavailable` (PAT-1732). A store that cannot be opened or read as a whole is `unavailable` and the `certificates` key is omitted, never sent as `[]`; a certificate that cannot be parsed is left out and the collection marked `partial`, with the key omitted when nothing parsed so an older server cannot read `[]` as "prune every row". macOS (`certs.sh`, `certs_payload_member` + `certs_collection_status`) and Windows (`CertCollector` + `CertCollectionLogic`) emit the same values. Each agent reads a fixed set of machine stores and reports every certificate in each of them, with no filter on subject, issuer or other certificate text (PAT-1737): Windows reads `LocalMachine\My`, `\Root` and `\CA` (PAT-1738 added `\Root` and `\CA`; `\AuthRoot` remains out of scope), macOS reads `/Library/Keychains/System.keychain` only, so Apple's `SystemRootCertificates.keychain` is out of scope by store choice. Every row carries a `store` field (Windows: `"My"`, `"Root"` or `"CA"`; macOS: the fixed value `"System"`) so classifying which rows are platform roots stays server-side, keyed on the row's store and thumbprint rather than its display text. The old Windows rule that dropped any subject containing "Microsoft" or "Windows" hid rogue certificates while still reporting `complete`, so the server pruned them. Classifying well-known platform certificates is server-side. Windows collects the three stores independently and combines them (`CertCollectionLogic.Combine`): only when all three are unavailable is the whole collection `unavailable`; one store unavailable while the others were read is `partial`, not `complete`, because `complete` would let the server prune stored rows for a store this run never actually looked at. `CertInventoryMapper` converts `NotAfter` (local time) to UTC before building the row; pairing it with a zero offset threw for any expiry outside UTC+0. macOS reads basicConstraints and extKeyUsage by walking the certificate's DER bytes itself (`openssl x509 -outform DER | od`, parsed in awk by position in TBSCertificate), never from `openssl x509 -text` or `openssl asn1parse`: both print attacker-controlled string values verbatim, and asn1parse also false-skipped valid certificates whose values print as text (PAT-1735, PAT-1740). Both agents classify CA and EKU only from one strict-DER extension of each (PAT-1735 macOS, PAT-1739 Windows): a repeated basicConstraints or extKeyUsage skips the certificate with reason `extensions_ambiguous`, a value that is not DER in the X.509 shape (a cA byte other than 0x00/0xFF, trailing bytes, an empty EKU) skips it with `der_unparseable`, and either makes the collection `partial`. Windows cannot rely on `cert.Extensions[oid]` (first match) or .NET's lenient decoders for this; `CertInventoryMapper` walks every extension and reads the value with `AsnReader` in DER mode. Apple's parser refuses a malformed basicConstraints outright, so the Windows fixtures for it only reach the mapper on Windows.

- **Installed apps report what they could read.** Top-level `collection_status.apps` is `complete`, `partial` or `unavailable` (PAT-2066, platform half PAT-2063), and unlike `certificates` an absent key is not read as complete. `complete` lets the server prune every stored app the array does not list, even an empty array, so it is only sent when the whole walk succeeded: macOS (`apps.sh`) needs `find` to exit 0 over every root and every top-level bundle to have a readable, parseable `Info.plist` (checked with `plutil -lint`, since PlistBuddy exits 0 on a file it cannot open); Windows (`InstalledAppScanner` + `AppCollectionLogic`) needs both HKLM Uninstall views enumerated and every subkey read. A failed listing, an unreadable bundle, a registry view that throws or is missing, or a subkey or value that throws is `partial`, with the rows that were read still sent; a scan that never finished (macOS stub) or threw outright (Windows) is `unavailable` with `apps: []`. Exclusions by design are scope, not failures, and never make the status `partial`: on macOS a helper bundle nested in another `.app` and a `.app` that is not a directory (an alias or other file), neither of which is ever inventoried and so never pruned; on Windows an entry with no display name or version, a system component, or a name and version already seen. A directory with `Contents/` whose `Info.plist` is missing or unparseable is still `partial`. iOS and iPadOS apps on Apple silicon (`WrappedBundle` or `Wrapper/` present with no `Contents/`) are in scope (PAT-2072): the identity comes from the one `Wrapper/*.app/Info.plist` and the row is an ordinary app row, so a wrapper with no inner app, more than one, or an unreadable or unparseable `Info.plist` is `partial`. `complete` covers the machine-wide scope only: HKLM on Windows and `/Applications` on macOS, iOS wrappers included. PAT-2075 collects loaded real-user HKU Uninstall paths and `/Users/*/Applications` separately: every row and its `collection_status.apps_users` entry use the same resolved account. Unlisted users grant no authority; failed users are partial. Never load logged-off hives or treat unresolved accounts as machine scope. Machine-only metering and installation/signature probes must not lend their evidence to user rows with matching identifiers.
- **App signing and notarisation are explicit, and "Unknown" is not unsigned.** `signed_by` is `"Unknown"` for an unsigned app, an ad hoc signed one and a codesign failure alike, and codesign never prints the word "Notarized", so the old `notarized` grep was false for every app (PAT-2112). `apps.sh` now sends `signing_status` (`signed`, `adhoc`, `unsigned`, `error`) from codesign's exit status and output, and `notarization_status` (`notarized`, `not_notarized`, `unknown`); `notarized` stays a boolean, true only for `notarized`. Notarisation is only asked of Developer ID apps (Apple and App Store apps are `not_notarized` without spctl), through `spctl --assess --type execute -vv` under a 10 second background-and-poll bound (`apps_spctl_assess`; macOS has no timeout(1) and spctl can go to the network), because many notarised apps are not stapled (VLC, Zed, zoom on tenant-zero). `Notarization Ticket=stapled` is only the fallback when spctl timed out, is missing or named no source; with neither the answer is `unknown`, never `not_notarized`. It costs time: about 45s a day on a Mac with 43 Developer ID apps (Chrome alone 6.6s). Both tools echo the bundle path, so the parsers read the last `source=` line, check `Signature=adhoc` before `Authority=`, and a path with a newline makes notarisation `unknown`. Every codesign field (`signed_by`, `team_id`, ad hoc, the stapled ticket) is read only from the lines after the last `CodeDirectory v=` line, because the path (`Executable=`) and the signing identifier (`Identifier=`, which `codesign -s - -i` accepts with newlines) both come before it and could otherwise plant `Authority=` or `TeamIdentifier=` lines; and a bundle whose path or executable path holds any control character, which `find -print0` now walks as one entry instead of dropping, is still sent but never given to codesign, spctl or lipo: `signed_by`/`team_id` `Unknown`, `signing_status` `error`, `notarization_status` `unknown` (PAT-2115). `codesign -dvv` does not evaluate trust: a self-signed certificate named `Developer ID Application: <anyone>` shows as that `Authority=`, though `TeamIdentifier` stays `not set`, so `team_id` is the publisher key and `signed_by` is display text only. Since PAT-2117 a signature -dvv shows with an `Authority=` is only `signed` after `codesign --verify --ignore-resources -R '=anchor apple generic'` (under a 10 second background-and-poll bound, `apps_codesign_verify`) exits 0: exit 3 (valid but not chained to Apple's root, e.g. self-signed) is `untrusted` with notarisation `not_notarized`, exit 1 (the signature does not validate against the executable or Info.plist) is `invalid` with notarisation `unknown`, and a timeout, missing codesign or any other exit is `error`, never `signed`. Only the exit status is read. The check covers the CodeDirectory, its signature and chain, every architecture of the main executable and the bound Info.plist, not resources or nested code: full resource validation took 39s a run on a Mac with 81 apps (Xcode alone 10 to 12s) against 8 to 13s without it, and `--strict` was dropped because it rejects zoom.us for Finder metadata Gatekeeper accepts. `untrusted` and `invalid` are new enum values: a platform whose CHECK (migration 0185) and extractor predate them stores NULL, not reported. Windows sends neither field (PAT-2113).
- **Safari extensions report what they could read, on their own signal.** Top-level `collection_status.safari_extensions` is `complete`, `partial` or `unavailable` (PAT-2067, macOS only; Windows has no Safari and must never send the key), and an absent key is no signal. `complete` lets the platform mark every stored Safari row the report omits as removed, even with no Safari rows at all, so `browser_extensions.sh` sends it only when `find` exited 0 over every search root (and, with the default roots, the home root could be listed, because under `NULL_GLOB` an unlistable `/Users` silently expands `/Users/*/Applications` to nothing), no symlink in the walk could hide an extension (`find` follows none and still exits 0, so a linked `~/Applications`, folder, app, `Contents` or `PlugIns` hides what is behind it; do not add `-L` as root). Every link in the walk is resolved once (zsh `:A`, a stat, nothing opened) and judged by `_bx_safari_link_harmless`: a target in the SIP allowlist (`/System/Applications`, `/System/Library` less its firmlinked subtrees, `/System/Cryptexes`, `/System/Volumes/Preboot/Cryptexes`) is harmless, never "anything under `/System`", because `:A` does not follow firmlinks and `/System/Volumes/Data` is the writable data volume; a `Contents/PlugIns` or appex link only when it lands on an in-bundle `*/Contents/PlugIns` path (any case); an `.app` or folder link inside a bundle only when it stays inside that bundle; a bundle's `Contents` link only in the allowlist; a folder link outside any bundle only in the allowlist; a file or dangling link with another name hides nothing. Without those two exceptions every current Mac reads `partial`. `complete` also needs a refusal log that was read and holds no refusal (a `grep` exit of 2 is not "none"), a parser that printed `#done`, and nothing in the array hit the 1,000-row cap (`cap_reached` false, including a user's fair share). A refused, unreadable or unparseable bundle, an unlisted root, or any cap is `partial` with the rows that were read; a parser that dies or cannot read the appex list before sending any Safari row is `unavailable`, and so is a collector that never ran. `find`'s stderr goes to the collect log, never `/dev/null`. The walk is a single `find` with no depth limit (PAT-2079): it lists every symlink and every appex on an any-case `Contents/PlugIns` path however deep, and every link is judged. Any depth limit is a silent one, because an appex past it is never listed and the walk still reads `complete`; do not add `-maxdepth` back, and do not flag app shapes past a limit instead, since helper apps nested in frameworks (every Chrome install) would pin every Mac at `partial`. More than `_BX_SAFARI_MAX_LINKS` (100,000) links is `partial`, which bounds the link work. The remaining exposure is cost: a user who fills their own `~/Applications` with a huge tree slows only their own device's collection. Before PAT-2067 an incomplete Safari walk also made `browser_extensions_status` partial (PAT-2065), because the platform's block authority covered Safari rows; since PAT-2064 it does not, so the block speaks for Chrome, Edge and Firefox only and the Safari walk never changes it, except that a cap hit anywhere is still `cap_reached`.
- **Security tools are detected by path and by Team ID, and a Team ID names a vendor, not a product.** `macos/lib/sectools.sh` keeps the path table and, since PAT-2234, also reads `systemextensionsctl list` (absolute path, `_SECTOOLS_SYSEXTCTL`) and reports a vendor from `_sectools_team_ids` only for an extension under the `com.apple.system_extension.endpoint_security` header that is enabled, active and `[activated enabled]`. The category matters: Bitdefender VPN is signed by the same Team ID (GUNFMW623Y) as Bitdefender Antivirus, so a network extension or an installed daemon under that Team ID proves the vendor is present, not that malware protection is running, and would put a false "covered" into EDR coverage and the Cyber Essentials malware control. For the same reason a shared Team ID (Microsoft's UBF8T346G9) is never seeded. A Team ID is seeded only from a `codesign -dv` of a real install that also passes `codesign --verify -R '=anchor apple generic and certificate leaf[subject.OU] = "<TEAMID>"'`, never from memory, and each row keeps the id and name of an existing path-table entry and matches the platform's `protected_software` baseline row (which matches reported tools by name). A non-zero exit, a missing binary, a missing count line, rows that do not add up to the count, or a seeded Team ID with no category header is logged as `Team ID detection undetermined` and never read as "no tools"; the payload has no field for it (`security_tools` items are `{id, name}`, `additionalProperties: false`), so the path table still runs. An inactive seeded extension and an Endpoint Security extension from an unseeded Team ID are logged, not reported.
- **Microsoft Defender for Endpoint needs positive onboarding evidence, never key existence (PAT-2270).** Windows includes `HKLM\SOFTWARE\Microsoft\Windows Advanced Threat Protection` and its `Status` key even when MDE is not onboarded. `SecurityToolDetector` reads `Status\OnboardingState` with the Windows registry type, and `SecurityToolLogic` reports `defender-for-endpoint` only for `REG_DWORD == 1`. A missing key/value or another DWORD is not onboarded; wrong types and read exceptions are undetermined, recorded as `mde_onboarding_failed` in `agent_health` under `collection_partial` / `security_tools`, never converted to absence. The next clean detection clears that degradation. Built-in Defender Antivirus remains a separate product, and other vendors retain their existing registry-key evidence. Sense service presence or state does not replace onboarding evidence.
- **Windows security tools read Security Center first, and a failed read is never "no tools".** `SecurityToolDetector` used to probe a fixed HKLM table and swallowed every exception as "not installed", and any vendor off the table was invisible (PAT-2267). `SecurityToolLogic` (Shared, unit tested) now reads Windows Security Center (`root\SecurityCenter2` `AntiVirusProduct`, `displayName` and `productState`) off Server, falls back to `MSFT_MpComputerStatus` for Defender wherever Security Center was not read, and always consults the registry table as a secondary signal, merging by id. Windows Server has no SecurityCenter2, so a `server` or `domain_controller` device class never asks for it and is complete from the fallbacks; a workstation or unknown class with SecurityCenter2 missing is undetermined. A product is reported only when `productState` decodes to a 24-bit value with the antivirus provider bit (0x04 in bits 16-23) set, whatever its on/off/snoozed state (the wire has no enabled field); an undecodable state, an empty or control-character display name, or a missing provider bit is not reported and makes the detection incomplete. Known vendor display names map to the table's existing id and name (whole-word prefix, case-insensitive), because the platform's `protected_software` baseline matches by name. Built-in Defender Antivirus (`Windows Defender`, `Microsoft Defender Antivirus`) is `microsoft-defender-antivirus`, never `defender-for-endpoint`: it registers on every client whether or not the device is onboarded to MDE, and the MDE name would mark every Windows device EDR-covered. Anything else gets a slug id (lowercase ASCII alphanumerics and hyphens, at most 64; `av-` plus 12 hex of SHA-256 when nothing survives; `wsc-` prefix if it equals a known id) and its display name bounded to 128 characters. `security_tools` is a required `{id, name}` array with `additionalProperties: false` and no status field, so the array carries only what was positively seen and an incomplete detection (a failed WMI query, a registry path that threw without a sibling proving the tool, an unusable Security Center entry) is recorded in agent_health as `collection_partial` / `security_tools` with the reasons, cleared by the next complete run. Omitting the key would reject the whole payload; the platform's EDR coverage report reads an empty array as `unknown`, not "no EDR".
- **Root is not exempt from macOS privacy protection (TCC).** Without Full Disk Access the root collector may `lstat` another app's data folder (Chrome, Edge, Firefox under `~/Library/Application Support`) but `open()` fails with `EPERM`. The shared walk helpers carry the errno (`lstat_kind`, and `list_dir`'s `Abort` has the `OSError` as `__cause__`), and `browser_extensions.sh` reports `EPERM` as the refusal `tcc_denied`, its own WARN, and the agent_health entry `tcc_denied` / `browser_extensions` / `full_disk_access_missing`; the pair stays `partial`, never `not_present` (PAT-2096). File opens carry it too (`open_regular_errno`, `read_file_errno`). Only the users walk counts toward the entry, and only the LaunchDaemon run (parent PID 1) writes or clears it; it clears only when the walk reached every folder (no cap, no failed home or browser). `mcp_servers.sh` (`~/Library/Application Support/Claude`, `.../Code/User`), `ide_extensions.sh` (`.../JetBrains`) and `package_managers.sh` (`.../fnm`, `.../pipx`) do the same with their own subject (PAT-2100): the issue code is `tcc_denied`, the client, user or source stays `failed` or `partial` and never `not_present` or `complete`, and `patched_tcc_health` (`common.sh`) applies the same daemon-only rule, reading the parser's summary line that starts `tcc ` (`tcc <count> <denied|reached|unknown>`, found by prefix via `patched_tcc_summary`; missing or garbled is `unknown`, no store change). The count is of unique denied folders or files, so one denied folder above several configs counts once, as `browser_extensions.sh` counts unique refused paths. It clears only on `reached`: not failed, not truncated, no failed home, and nothing refused with any errno. The Safari walk's `find_manifest` logs a `Contents/Resources` folder it cannot list (PAT-2100) rather than sending the bundle with no permissions in silence, so Safari is then `partial`. **Never grant Full Disk Access to `/bin/zsh`, `/bin/bash` or Terminal**: any local user can run them, so any user could read every user's data. A supported grant needs a signed collector binary (PAT-7, PAT-9).
- **Windows signs most of what it ships by catalog, not by embedded Authenticode.** `WinVerifyTrust` against a file handle alone answers `TRUST_E_NOSIGNATURE` (`0x800B0100`) for `powershell.exe`, `notepad.exe` and the rest of System32, so a file-only reader reports the whole operating system as unsigned and cannot tell a genuinely Microsoft-signed OS binary from an unsigned one (PAT-1981, found under PAT-1971). `WindowsInstallationEvidence.ReadSignature` now falls back to the catalog store on that code and on `TRUST_E_SUBJECT_FORM_UNKNOWN` (`0x800B0003`, what a file wintrust cannot parse as a subject returns), and on nothing else: `TRUST_E_BAD_DIGEST` (`0x80096010`) is an answer, not a gap, so a tampered embedded signature is never re-asked as a catalog lookup. The lookup is `CryptCATAdminAcquireContext2` + `CalcHashFromFileHandle2` with **SHA-256 only** — the non-`2` entry points hard-code SHA-1, and a catalog is a signed hash-to-file binding, so honouring a SHA-1 membership would make a SHA-1 collision enough to earn `"valid"` and a Microsoft signer. A file whose only catalog entry is SHA-1 stays `"unknown"`. Any catalog failure (no context, no hash, an enumeration error, catalog will not verify) leaves the embedded `"unknown"` standing and never becomes `"invalid"` or a fabricated `"valid"`. **`"unsigned"` (PAT-2116) is the conservative exception, decided only in `SignatureVerdictLogic.Decide` (Shared, unit tested):** the embedded check returned exactly `TRUST_E_NOSIGNATURE` (never `TRUST_E_SUBJECT_FORM_UNKNOWN`), the SHA-256 catalog lookup *ran* and found no catalog (the first `CryptCATAdminEnumCatalogFromHash` returned NULL with `GetLastError() == ERROR_NOT_FOUND`, 1168; any other error is a failure), a SHA-1 membership lookup also found none (a SHA-1-only catalog member is withheld from `"unsigned"`, though still never honoured as `"valid"`), and the catalog database found `chkdsk.exe` or `powershell.exe` as a SHA-256 member in the same helper run. Anything short of all four is `"unknown"`. The ERROR_NOT_FOUND code is unverified on a device from this Mac; `ModifiedCopyOfACatalogSignedBinaryIsUnsignedWhileTheIntactCopyStaysValid` on the `windows-latest` job is the check, and if it reads `"unknown"` the fail-safe held and the code is wrong. One file's hash is commonly in several catalogs (12 for `chkdsk.exe` on Windows 11 26100), so the enumeration is walked rather than stopped at the first, and `CryptCATAdminEnumCatalogFromHash` releases the context handed to it — surrender ownership before the call and retake it from the result, or you double-release. Release the catalog context before the admin context that issued it. Both subject forms run through the same `WinVerifyTrust` call with `WTD_CACHE_ONLY_URL_RETRIEVAL | WTD_REVOCATION_CHECK_NONE`, so a catalog `"valid"` carries the same offline, no-revocation caveat as an embedded one, and `WTHelperProvDataFromStateData` populates identically for both, so one signer extraction serves both. That extraction also yields PAT-2116's pinnable publisher, only beside `"valid"`: `signer_thumbprint` (leaf SHA-256), `issuer` (leaf Issuer DN), and `root_thumbprint`/`root_kind` from the last certificate of the same provider chain (`CRYPT_PROVIDER_SGNR.csCertChain - 1`), never a second chain build. `root_kind` is `microsoft` for the four hard-coded Microsoft product roots in `AuthenticodeRootClassifier`, `public` for a self-issued root in the registry `AuthRoot` physical store (auto root update; Group Policy and Enterprise physical stores deliberately not read), and `enterprise` for everything else, including anything uncertain. Microsoft Identity Verification Root CA 2020 (Trusted Signing) vouches for third parties and is `public`, not `microsoft`.
- **Windows Authenticode evidence covers every app row, not just reviewed targets (PAT-2116).** `AppSignatureCoverage` (Shared, pure) runs after the reviewed-target collector and never overwrites its rows; `AppSignatureCoverageProbe` (`--collect-app-signatures`) is a second killable helper on the same trusted-helper boundary (`InstallationEvidenceProbe.PrepareTrustedHelper`). Only row indexes, ARP subkey names and the registry view go to the helper, on stdin; it reads the Uninstall values from HKLM itself. `ExecutableResolver` accepts only a hint strictly inside a Program Files root and outside the Windows directory (shared OS binaries and `%WINDIR%\Installer` icon stubs would lend Microsoft's signature to third-party rows; user-writable paths would be read as LocalSystem): a `DisplayIcon` .exe (inside `InstallLocation` when that is present), else exactly one candidate top-level .exe in `InstallLocation`, listed through the same locked, reparse-refusing walk. PAT-2129 added, from WIN-STAGING evidence (1 of 10 rows resolved on 0.14.3): a product-name-matched exe in `InstallLocation`'s top level, `cmd\` or `bin\` (Git, PowerToys); the same name match in `UninstallString`'s directory when there is no `InstallLocation`, never the lone exe there (UTM Guest Tools' is a bundled `vc_redist`); and an MSI product's `.exe` component key paths via `MsiComponentReader` (read-only package open under the locked walk, `MsiGetComponentPath` only), single or name-matched (Spice webdavd, Tailscale). A candidate is never uninstaller- or `redist`-named, and the name match drops only a closed list of trailing version, architecture and channel qualifiers. Anything else, and one exe claimed by two rows, is `unknown`; never a guess. Every row's `executable_resolution` now carries the method or a reason (`not_applicable`, `unresolved_ambiguous`, `unresolved_not_found`, `unresolved_outside_roots`, `unresolved_listing_unavailable`, `unresolved_no_hint`, `unresolved_registry_unavailable`, `unresolved_not_attempted`), each within the platform's 0188 CHECK. `not_applicable` needs the whole evidence pattern (a Microsoft Burn bundle with no `InstallLocation`, named exactly as the VC++ Redistributable or .NET SDK bundles are), because PowerToys has the same bundle shape and a real app; a new pattern needs device evidence. Bounds: 10 s per step (the helper prints a line before every target's IO, so a hang is attributable and that one row is `collection_timeout`), 45 s and at most 6 helpers per scan (the rest `collection_budget_exhausted`), 1,024 rows. Verdicts are cached in service memory by SHA-256 + size + mtime (24 h, `unknown` 1 h), sent to the helper on stdin, never written to disk. The platform stores `unsigned` as NULL until its follow-up in `docs/windows-installation-evidence.md` ships. The helper's own directory, `%ProgramFiles%\Patched`, is judged by `WindowsInstallationEvidence.VerifyInstallDirectoryAcl`, not `SecureStagingDirectory.VerifyTrusted`: an MSI-created directory inherits `%ProgramFiles%`' DACL (TrustedInstaller FullControl plus inherit-only `GENERIC_ALL` for CREATOR OWNER), which `VerifyTrusted` rejects, so 0.14.2 reported `helper_failed` for every app on every real install while the CI tests, which never run from Program Files, stayed green. TrustedInstaller counts as a trusted writer there and inherit-only ACEs are ignored; any other write-capable grant still fails closed. `VerifyTrusted` stays the policy for directories the agent creates and hardens itself. A refused preflight is never silent: the rows say `helper_preflight_refused` (kept apart from `helper_failed`, a helper that started and then crashed, and `collection_timeout`), `HelperPreflightReporter` logs one WARN per cycle naming the check and, for an ACL refusal, the offending principal SID and rights, and agent-health carries `helper_preflight` / `app_signatures` (or `installation_evidence`) / a fixed reason code (`location_untrusted`, `install_dir_owner`, `install_dir_acl`, `executable_owner`, `executable_acl`, `install_path_unavailable`, `preflight_error`) until a preflight passes. The SID stays in the local log, never on the wire.

- **Usage absence needs per-app evidence (PAT-2328).** A loaded HKU hive is not usable UserAssist history: Windows `ok` requires at least one positive-count/date record and no failed or explicitly disabled loaded hive. `Start_TrackProgs` DWORD 0 excludes that hive's historical records; missing is not proof of working tracking. Per-app `usage_evidence` is `recorded`, `no_record`, `unmapped` or `unavailable`; no_record never proves non-use. A bare install directory and a service/runtime icon are not desktop-executable evidence. Only sampled exact Edge/Office AppIDs have closed bindings; never execute or resolve shortcuts as LocalSystem. On macOS, check both mdls exit codes before classifying successful nulls: errors, malformed output and the 1980 sentinel are unavailable. The collector and payload stub default metering_status to unavailable, committing the probed source status only after the app walk completes; spotlight_disabled requires a successful explicit disabled probe. See docs/windows-metering-adr.md for scope and historical-report limits.
