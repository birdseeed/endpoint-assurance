## Scan deletion left data in marked-deleted rows: patched in source; reviewed source; native behaviour unverified

The public scan delete/sweep path could leave email, company, IP, OTP and report-token values in rows already marked deleted. The source-only patch now deletes a row only after cleanup of its owned file; if unlink fails, it revokes PII, OTP and download access immediately, records pending paths and a delete token for retry, returns 503, and uses 409 for a busy guard. Legacy tombstones are retried automatically. A separate quota ledger preserves email/IP limits for only the remainder of the original 24-hour window, using per-record keyed digests and an opaque scan hash. The stored key permits candidate matching, so these records are pseudonymous, not irreversibly anonymous; they contain no raw email, IP, company, OTP or bearer capabilities. Expired records stop counting and are purged on rate checks and retention sweeps; inactive storage can await the next sweep. Already-erased legacy identities cannot be reconstructed. A cross-process guard remains held through spawned-writer operating-system exit, including when the supervisor is killed.

The patch's automated scan suite passed **281 tests with no skips**; parent verification also covered **17 focused process/erasure checks and 8 quota checks**. These used synthetic SQLite and outbound guards. No live database cleanup or deployment occurred. The source patch completed independent whole-patch review and was merged before this archival update; this does not establish live cleanup.

## Windows enrolment credential source: medium, conditional; candidate patch pending native closure

The frozen baseline Windows service path has a conditional local credential-integrity risk. The state-root ACL repair in `Program.cs` and log-directory hardening do not authenticate credential descendants. `CredentialStore.ReadCredsFile` reads the selected file with `File.ReadAllText`. A local non-administrator legacy write window, or a remaining writable child directory, could let a local writer plant a valid attacker-tenant enrolment key on an unprovisioned device without an overriding Credential Manager or environment identity. LocalSystem could then enrol the machine and post inventory to that tenant.

This does not establish a default installation, public exploit, remote code execution or native exploit. Counterevidence includes root ownership and reparse checks, safe installer-token provisioning, and Credential Manager/environment identity priority. The issue is not a credential leaked in the GitHub repository. A 2 November source candidate adds bound-owner checks, root/credential/leaf privacy ACL handling, refusal of unsafe legacy references without repair, safe root UI reads, and preserves token, marker, Credential Manager, environment and registry semantics. It hardens only an empty integrity-trusted store before fresh secret provisioning; a non-empty store with exposed credentials is left unchanged and requires reprovisioning. The candidate is not declared fixed: native Windows closure checks remain required.

Candidate verification recorded 2 November: independent Astra static review passed after repair of a readable-token regression. Shared checks report 2,172 passed and 16 skipped, including 15 native Windows fixtures that were not run. Verifier cross-build reports zero warnings/errors. Python auth (37), dashboard (179), and scan (281) suites passed; hashed-lock installs, pip checks and certificate smoke checks passed. The exact Go 1.27.2 toolchain was unavailable; Go 1.27.1 remains affected by GO-2026-6601 and GO-2026-6602, whose fixed toolchain boundary is 1.27.2. Exact Node 24.21.0/npm 11.19.0 and Go 1.27.2 checks and the fifteen native Windows fixtures were not run. Native validation and exact toolchain checks remain required before any run or reuse.  These results do not close native Windows behaviour or release readiness.
